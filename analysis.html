Polars 2.1: Memory use in overlapping 60-month windows

Published

October 27, 2026

Several months ago, I wrote a Polars query to estimate 60-month betas for each firm and month from daily stock-return data. It divides the covariance of market and firm returns by the market-return variance. The original query used over 80 GB before failing on my Mac mini M4 Pro, which has 24 GiB RAM. I moved it to DuckDB.

Polars 2.1 did not resolve the memory issue by itself. Its unmodified covariance/correlation path still expands overlapping windows into large lists. A candidate patch, now compiled and tested, avoids that expansion for the multi-input aggregation path and for the direct cov_alt() formula. On the original 25-million-row synthetic beta query, it reduced footprint from about 24.45 GiB to 1.96 GiB, with bit-for-bit identical results.

The original query

The query originated in the Tidy Finance beta-estimation example. My original analysis source contains the earlier generator and benchmark.

import polars as pl

def build_results_lz(min_obs: int = 1000) -> pl.LazyFrame:
    return (
        pl.scan_parquet("synthetic.parquet")
        .group_by_dynamic(
            "date",
            every="1mo",
            period="60mo",
            offset="-60mo",
            group_by="firm_id",
            closed="left",
            label="right",
        )
        .agg(
            beta=pl.cov("mkt_excess", "ret_excess") / pl.col("mkt_excess").var(),
            mean_ret=pl.col("ret_excess").mean(),
            mean_mkt=pl.col("mkt_excess").mean(),
            n=pl.len(),
        )
        .filter(pl.col("n") >= min_obs)
    )

results = build_results_lz().collect()

The existing synthetic input has 10,000 firms × 2,500 days = 25,000,000 rows. It was reused for the before/after check. Input SHA-256: 42a4f6fc9747e2636c51e7de06b62433a3a0d0b7e6e922dd3159f38666712309.

Aligning DuckDB with Polars

The DuckDB comparison now evaluates the same window-label grid as Polars. Per firm, it generates monthly labels through 60 months after the last input month, appends null-valued evaluation rows, and evaluates the same half-open 60-month intervals. count(observation) counts real input rows, so evaluation rows affect neither observation counts nor covariance. The only output threshold is n >= 1000, in both engines. No last-input-date filter is added to Polars.

This gives 77,000 rows in each smaller reproducer and 770,000 rows in each original full-size result, including the later labels produced by Polars. A separate smoke check also passed with weekday-only observations and null values. The earlier SQL that retained only dates present in the input is retained as historical provenance, not used as the current comparator.

The smaller reproducer uses this SQL for covariance:

WITH observations AS (
    SELECT firm_id, date, x, y FROM 'synthetic.parquet'
), bounds AS (
    SELECT firm_id,
           date_trunc('month', min(date)) + INTERVAL 1 MONTH AS first_label,
           date_trunc('month', max(date)) + INTERVAL 60 MONTH AS last_label
    FROM observations GROUP BY firm_id
), evaluation_points AS (
    SELECT firm_id,
           unnest(generate_series(first_label, last_label, INTERVAL 1 MONTH))::DATE AS date
    FROM bounds
), window_input AS (
    SELECT firm_id, date, x, y, 1 AS observation, false AS is_evaluation
    FROM observations
    UNION ALL
    SELECT firm_id, date, NULL::DOUBLE, NULL::DOUBLE, NULL::INTEGER, true
    FROM evaluation_points
)
SELECT firm_id, date, covar_samp(x, y) OVER w AS value,
       count(observation) OVER w AS n
FROM window_input
WINDOW w AS (
    PARTITION BY firm_id ORDER BY date
    RANGE BETWEEN INTERVAL 60 MONTH PRECEDING
              AND INTERVAL 1 DAY PRECEDING
)
QUALIFY is_evaluation AND count(observation) OVER w >= 1000
ORDER BY firm_id, date

The original full-size comparison uses the same grid and frame, with covariance divided by market-return variance and the two means added to the output.

Implementation and tested fix

The Polars 2.1 source suggests that the memory expansion occurs before the numerical covariance kernel:

  1. The multi-input group-aware apply path calls iter_groups() on each input. For an unaggregated input, that calls aggregated(), which calls agg_list(). See multi-input apply, group iteration and aggregation context.
  2. For numeric slice groups, agg_list() appends each window’s values to a new list-values buffer. Overlapping values are therefore copied repeatedly. See numeric list aggregation.
  3. Mean and variance have specialized aggregation paths, including rolling kernels that operate on the original values and window offsets. See mean and variance.
  4. The single-input apply path already has a lazy iteration branch for overlapping groups. The corresponding multi-input path does not use it. See the existing safeguard. The low-level covariance function itself uses an accumulator state; it does not require all windows to be copied at once (kernel).

This is a static source trace, not an allocation-profiler trace. However, it also predicts the observed scale: these 2,500,000 input rows participate in 150,000,000 window memberships before the output filters. Copying two Float64 values per membership takes 2,400,000,000 bytes (2.24 GiB), before vector capacity, input columns, output arrays and other overhead. The measured footprint is about 2.57 GiB.

The candidate patch has now been built against the exact Polars 2.1.0 release commit, using its pinned nightly-2026-09-01 toolchain, default full runtime features, 32-bit indices and the optimized nodebug-release profile. Python was 3.14.2 throughout.

The official wheel uses dist-release (fat LTO); the local build used thin LTO. Timings therefore include a build-profile difference. The before/after memory reduction and exact numerical comparisons are the principal checks here. Build provenance records the commit, patch hash, wheel hash and both imported native-module hashes.

All 26 Polars benchmark outputs and the 240 original edge cases are bit-for-bit identical before and after the patch. The 384 additional composed-expression scenarios have identical values, null/NaN positions and non-NaN floating-point bits. Some NaN bit patterns differ between the official and local builds; the same differences were present in the earlier compiled patch. 1674 upstream tests passed. The aligned DuckDB result has the same full keys and observation counts and agrees within floating-point precision. These checks do not constitute the entire Polars test suite.

The candidate extends the existing lazy overlapping-group iteration to multi-input apply when all inputs are unaggregated overlapping slice groups. Each input then yields one view of its original values per window, rather than first building the large expanded lists. The other states retain the eager path. Patch, implementation notes and build instructions are available.

The book’s cov_alt() expression uses a separate binary group-aware path. That path materializes the centered inputs and their product for every overlapping window. The first ApplyExpr patch left its footprint at about 4.89 GiB.

The extended patch recognizes Float64 arithmetic over columns, column means and literals feeding a sum on the original overlapping slice groups. It computes the means through the existing aggregation kernels, then evaluates and sums one window at a time. It preserves the expression’s independent means, null handling, denominator and arithmetic order; it does not replace the expression with pairwise-complete covariance. The measured footprint is now 0.298 GiB, versus 4.892 GiB on released 2.1, with bit-for-bit identical output. Other expression types and group layouts retain their existing evaluation paths. This is a scoped candidate, not a general solution for every composed aggregation.

A separate comparison keeps the build profile fixed: both local wheels use nodebug-release with thin LTO. Across three alternating fresh-process runs, cov_alt() changed from 1.791 seconds and 4.856 GiB with the first patch to 0.299 seconds and 0.297 GiB with the extended patch. The output is bit-for-bit identical.

Two candidate patches

Both candidate fixes change Polars’ Rust execution engine. The Python cov_alt() formula is unchanged.

  • Multi-input apply patch: lazy window views for covariance, correlation and other multi-input grouped functions.
  • Composed-sum patch: evaluate and sum Float64 arithmetic over columns and column means one overlapping window at a time.
  • Combined patch: the exact source change used for the final build and numerical validation.

The separate patches are supplied for review. The final benchmark and regression results were recorded with both applied; the earlier multi-input-only build also provides the same-profile control.

What about spilling in Polars 2.1?

This keyed dynamic aggregation still appears as an in-memory-map fallback. The native streaming path requires no additional grouping keys. The new group-by spilling and window spilling operate on supported streaming nodes. The tested fix reduces covariance/correlation memory within the existing fallback; it does not add a streaming operator.
